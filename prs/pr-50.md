# pr/50: Faster block parent lookup in the store
{: .no_toc }

Branch `pr/50-store-parent-index` · base `pr/42` (no dependency on it) ·
1 commit · 2 files, +226
{: .fs-3 .text-grey-dk-000 }

## Why

Typing on a long page gets slow. A Firefox profile of typing in a 500-paragraph
page of plain text showed `store.getParent()` and the root lookup taking
**about a third of all JavaScript per keystroke**.

Both scan every block in the doc to find the one whose children include the
given id. Many code paths call them once per block, such as selection,
rendering and commands. A full re-render was therefore quadratic in the
number of blocks.

## What changes

`getParent()` and the root lookup use a cached index. A parent lookup is a map
read instead of a scan of the whole doc. Typing on long pages is noticeably
more responsive.

Behaviour is otherwise unchanged.

## How it works

In `blocksuite/framework/store/src/model/store/crud.ts`:

- **The index.** A child-id → parent-id map, built lazily per Yjs blocks map
  and held in a `WeakMap`, so it goes away with the doc.
- **Invalidation.**
  - The index is dropped on any structural change: through the store's own
    `addBlock`, `deleteBlock`, `moveBlocks` and `updateBlockChildren`, and
    through a Yjs `beforeObserverCalls` hook. The hook covers remote updates
    and undo/redo.
  - It is rebuilt on the next lookup.
  - The Yjs hook is installed only once an index exists, so stores that never
    look up parents pay nothing.
- **The root id** is cached the same way.

## Testing

Unit tests: `parent-lookup.unit.spec.ts` checks three things:

- repeated lookups don't walk the whole document
- lookups stay correct across add, move and delete
- lookups stay correct when the structure changes outside the store API, as
  with a remote update or undo
