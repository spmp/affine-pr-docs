## Why

Bugs in focus, caret, keyboard and scroll timing on iOS show up only on a
real device. Automated browsers don't reproduce them. Safari's Web Inspector
needs a Mac and a cable, and it can't be scripted. A developer, or a coding
agent, needs a faster way to see what is happening on the device and to try
a fix on it.

## What changes

Two server endpoints and their clients. Both are **off unless enabled** in
server config:

- **Debug-log upload** (`/api/mobile-debug-log`):
  - The mobile app can send captured debug logs to the server.
  - Only signed-in users can upload.
- **Remote eval** (`/api/mobile-debug-eval`):
  - A developer submits a JavaScript snippet with a token.
  - The mobile app polls for snippets, runs them and posts the result back.
  - Enabled only with `AFFINE_MOBILE_DEBUG_EVAL_ENABLED`.

`scripts/mobile-debug-eval.sh` submits a snippet and prints the result.
`docs/mobile-debug-workflow.md` describes the whole debugging loop. Debug
builds also expose the mobile app's DI framework, so snippets can reach
services.

## Testing

- Server tests: the debug-log controller.
- Unit tests: mobile debug-log capture.
- E2E: a WebKit test proves the log upload works end to end.

## Status

**Probably fork-only**, or offered upstream as a developer-only feature.
Before it is offered:

1. **Security, first.**
   - **Who can run snippets.** Today `/pending` and `/result` are public, and
      the mobile app polls for every user. With eval enabled, a snippet runs
      on whichever device polls first. Delivery must be limited to signed-in,
      allow-listed users. Every command must be logged, and the poll loop
      must start only when the server enables it for that user.
2. **Desktop web client.** Install the same client in the desktop web app.
3. **Client targeting.** Clients register, and commands go to a chosen
   client.
4. **Long-polling** instead of 1–2 s polling.
5. **Agent tooling.** An MCP server wrapping the CLI.
